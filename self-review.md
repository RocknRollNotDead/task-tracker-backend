## Бэкенд

### package config

**Properties классы** - очень хорошо. Не дают подняться спрингу если нет значений в `application.yml`.

**UsersDbInitializer** - для разработки хорошо, но во-первых здесь нет разделения на admin и user, поэтому одной роли достаточно, во-вторых здесь это вообще бессмысленно, потому что основной ручной тест - проверка почты, а почту лучше регать самому. 1. в `.env` лучше не занимать место, меньше переменных - понятнее программа, 2. одна из функций программы - после регистрации приходит письмо на email, и именно это можно проверять ручным тестом.
Рекомендация - удалить класс.

**KafkaProducerConfig** - url и название продюссера лучше вынести в пропертиес, также как jwt-secret. Это уменьшит хардкод

### package security

**Logout.**

В `SecurityConfig` разрешается ходить на эндпоинт `/logout` всем. В auth контроллере проверяется наличие сессии и кидает `BadCreditals`. По-хорошему надо ловить это в Security. Потому что сейчас запрос идёт в `JwtFilter`, там пытается парситься токен, и при ошибке возвращается 401. Во-первых это мёртвый код, запрос никогда не дойдёт до контроллера, так как всегда оборвётся на фильтре. Во-вторых лучше кидать свои исключения. В третьих парс токена - это лишняя работа программы, которую можно избежать, поставив ограничение в `SecurityConfig`, тогда запрос даже не дойдёт до парса jwt. Стоит убрать проверку из auth контроллера.

В Intellij idea в любом файле справа есть линия, за которую лучше не заходить. При заходе за эту линию код становится плохо читаемым. Лучше переносить.

В `SecurityConfig`, как и в других классах, используются инжекция через конструктор. При изменении полей придётся убирать поля, потом ставить другие. Вместо этого есть аннотация из ломбока. Тем более уже есть неиспользуемая аннотация `@Slf4j`.

**Jwt** - хардкод во времени жизни токена. Стоит подумать, как вынести, чтобы только в `application.yml` прописывать `7d`, `1d`, `4h`, как со временем сессии.

### package controller

В методах `logIn` и `createUser` дублируется логика аутентификации и дачи токена. Стоит вынести её в `AuthenticationService`, чтобы возвращать сразу токен, а не principal. Тогда и не придётся инжектить `jwtService`, на котором сейчас зависимость. (я не могу изменить способ auth не трогая контроллеры) Но вообще при фильтре этого не нужно - проверка на null и так мертвый код.

`logOut` - если не удалять мёртвый код (проверка на null), то стоит хотя бы вынести проверку в аннотация `@NotNull`, которая уже есть в user контроллере в `getInfo`, для однообразности кода.

**TaskController**

`createTask` - тоже самое, валидацию null стоит вынести в аннотацию. Тут уже не удалить, потому что это клиент присылает, и никто не контроллирует это.

`executeTask`, `editTask`, `deleteTask` - как раз нет этой проверки, хотя должна быть, вдруг клиент передаст null. Может упасть `NullPointerException`. Серьёзный баг в коде, который требует исправления.

### package service/util

**TaskService** - классный тонкий сервис. Единственное, мапперы, которые используются в сервисах, можно сделать с помощью MapStruct. Ручные мапперы ничем не хуже, просто пишу о необходимости знать что такое MapStruct. Единственное - забытое "User from session not found!". Во-первых сессий уже нет, они были на предыдущем проекте, а во-вторых детали хранения не стоит сообщать. Лучше "User with this Id not found!"

**UserService** - исключение сообщает "User not found in db", что раскрывает способ хранения наружу. Хотя security перехватывает неавторизованного пользователя, всё равно в сервисах раскрывать детали в исключениях не стоит.

Сохранение в кафку реализовано так - `UserService` без `@Transactional` вызывает `UserSaverService`, где уже есть `@Transactional`. Это позволяет не останавливаться при зависании на кафке. Решение допустимо, но советую почитать про паттерн Transactional OutBox.

Также название метода `userSaverService.saveUserToRepository` дублирует название класса. Лучше было бы `execute`. Детали "ToRepository" тоже вызывающему сервису не нужно знать. Это мешает расширяемости. Код `UserService` не должен зависеть от того, куда мы сохраняем юзера.

`TEXT_WELCOME_MAIL_MUST_BE_FORMATTED` в `EmailSenderService`. Идея хорошая, имеет место быть, но лучше создать отдельный класс, где метод будет отдавать уже полное письмо. Классы не должны зависеть от реализаций того, что они вызывают.

То, что основной сервис вызывает сервис "послать email", а сервис "послать email" посылает в кафку, классное разделение ответственности. Главный сервис говорит "пошли email", а сервис "послать email" уже сам разбирается как это реализовать.

### package dao

Ещё отмечу правильное использование JPA, возможности которого достаточны, чтобы не сортировать/проверять принадлежность в сервисе, а сразу запрашивать такое из бд.

Единственное замечание, надо привести к единообразию запросов `findBy` и `getTaskBy`. Я склоняюсь к рекомаендации `findBy`, потому что и так понятно, что репозиторий ищет `Task`.

### package model

Отмечу неочевидный `FetchType.LAZY`. Хорошо предусмотрено, незачем гонять лишние сущности туда-сюда, ведь все вызовы идут в транзакциях.

Ещё замечу, что у Hibernate есть аннотация `@Enumerated`, которая превращает хранение в String. Сейчас enum там хранятся в виде цифр. Это тоже неплохое решение, даже лучше хранения String, но мне кажется важно упомянуть об этом.

### package dto

Хорошее разделение по пакетам, хорошая валидация на классе, сказать практически нечего. Единственное - забыто сообщение при `@NotNull` на поле `text` в `RequestTaskDto` - если фронтенд отправит null вместо "", пользователю вылетит unknown в сообщении об ошибке.

### package exception

Исключений лишних нет, единственное, если убирать бесполезную проверку на null в `/logout` и убрать выброс `BadCredentials`, то обработчик такого исключения из handler стоит убрать - оно больше нигде не выбросится.
